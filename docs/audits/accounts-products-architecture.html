1. Motivation

The wallet app had no domain/service layer: every route called the bloque SDK client directly inline inside useQuery/useMutation, and SDK response shapes were the app's own types, scattered across dozens of files with local as unknown as X casts. Two real bugs shipped from exactly that pattern before this revamp started:

  • A BRE-B send flow silently debited whichever BRE-B key happened to sort first in the list, regardless of user intent.
  • Accounts sharing the same underlying ledger were iterated naively, double- and triple-counting the same balance.

Two things converged to turn "fix these bugs" into "fix the pattern that produces them":

  1. @bloque/sdk-accounts shipped 0.2.5/0.2.6/0.2.7 the same day this work started. Diffed against the previously pinned 0.2.4: it adds a program field to cards (multi-program support) but does not fix a separate, confirmed gap — bloque.accounts.list() only tags an explicit medium field on BRE-B accounts; every other type (card, virtual, Polygon, Bancolombia…) omits it.
  2. A future SDK version (v0.3 or v1.0, not yet published) is expected to formalize a User 1—* Account 1—* Product model server-side, which should fix that gap at the source. Rather than build more UI on top of the leaky, cast-heavy access pattern, this work introduces a lightweight hexagonal seam now — so when the real model lands, only one adapter needs to change.

Design constraint: plain TypeScript domain types + a repository "port" (a function-signature type, not a class/interface-with-implements) + one adapter implementing it against bloque — no DI container, no classes. This matches the codebase's existing 100%-functional style; the goal was a seam, not a framework.

2. Architecture overview

Routes never import bloque directly for accounts/cards/BRE-B/Polygon/pockets anymore. They call React Query hooks, which call a plain-function port, implemented by exactly one adapter that talks to the SDK and maps its (occasionally unreliable) shapes into clean domain types.

3. Domain model

Product is a discriminated union tagged by kind. A virtual pocket is just another tagged member of that union (kind: 'pocket') rather than a separate field on Account — this was a deliberate call after review: splitting it out would force every consumer (the associated-products list, "N products" counts, the create-product flow) to special-case "is there a pocket" and then merge it back in wherever the full membership is needed.

Also confirmed live: every product sharing a ledger returns an identical balance array regardless of which member's URN is queried — balance (and very likely movement history) is a ledger-level property, not a per-medium one. This is why Account.balances is simply its primary product's balances, with no summing required.

8. Known gaps & deliberate scope cuts

Called out explicitly rather than left silent:

  • Medium duck-typing shim (src/infra/bloque/accounts-repository.ts) — works around the SDK only tagging medium on BRE-B accounts. Clearly commented as temporary; delete once a future SDK version tags every type properly.
  • send/colombian-banks/index.tsx — migrated its data source only. It still silently funds bank transfers from whichever card sorts first — the exact same class of bug fixed everywhere else in this work, found but intentionally not fixed here to keep this pass's scope contained. Flagged for a follow-up.
  • card/details/-hooks/use-accounts.ts (per-card balance/movements) and (home)/-hooks/use-balance.tsx (aggregate home balance) — left calling bloque directly. Neither has a known bug and both are tangential to the ledger-grouping/medium-detection problem this work targets; migrating them was judged not worth the added diff size this pass.
  • Payments/swap/topup/KYC — entirely out of scope, per the Phase 6 roadmap below.

9. Verification

  • bun run typecheck — clean after every phase and every commit (enforced by the pre-commit hook too).
  • biome check — zero new lint issues across all touched/new files.
  • bun run build — full production build succeeds twice (after the dead-route deletion, and again at the end).
  • groupIntoAccounts() exercised against a hand-built Product[] mirroring the real production data pulled via mcp__bloque__list_accounts — reproduces the confirmed 4-group shape (Fig. 4) exactly, including the "dangling card is actually tied to a pocket" and "empty pocket, zero products" edge cases.
  • Not done: live-browser QA — no authenticated session was available in this environment. Recommended before shipping: manually click through /accounts, /accounts/$urn, card creation from Account Detail, and the BRE-B manage-keys?ledgerId= bypass.

10. Roadmap (Phase 6, not built this pass)

Once this pattern proves out, the same shape should extend to:

  • Payments/transfers (topup, convert, send, swap rates) → a SwapRepository wrapping bloque.swap.*.
  • KYC/compliance → a ComplianceRepository wrapping bloque.compliance.*.
  • Movements/transactions → partially overlaps this domain already; needs its own scoping pass once Accounts/Products is stable.
  • Auth/session → lowest priority; already has its own differently-shaped context.

Same rule each time: plain function-signature ports, no classes/DI, one adapter per domain, migrated route-by-route rather than all at once.
